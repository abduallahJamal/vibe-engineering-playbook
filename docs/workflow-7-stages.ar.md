# منهجية الهندسة الوكيلية في ٧ مراحل (من الفكرة إلى الإنتاج)

**[🇬🇧 English Version](workflow-7-stages.en.md)** · **[⬅ العودة إلى الدليل الرئيسي](../README.ar.md)**

الانتقال من «الفايب كودينج» العشوائي إلى **الهندسة الوكيلية المنضبطة (`Vibe / Agentic Engineering`)** يمر عبر سبع مراحل متتابعة، لكل مرحلة مخرجات مكتوبة ومعيار عبور واضح لا يُتجاوز.

---

## خريطة المراحل السبع

</div>

```text
1. الاستجواب واستكشاف المتطلبات (Grilling)
        │
        ▼
2. تصميم النظام والمواصفات  ──►  AGENTS.md + PRD.md + مصفوفة الحالات الحدية
        │
        ▼
3. إعداد البيئة وأقل الصلاحيات  ──►  Git + .env + Linter + عزل البيئة
        │
        ▼
4. وضع التخطيط والاعتماد  ──►  IMPLEMENTATION_PLAN.md (معتمدة بشرياً)
        │
        ▼
5. البناء المتسلسل ونقاط الرجوع  ──►  مهمة واحدة + قراءة Diff + Atomic Commits
        │
        ▼
6. النقد الصارم والمسارات غير السعيدة  ──►  الأمان · الأداء · قابلية الصيانة
        │
        ▼
7. بوابة الإطلاق والبناء لمن بعدك  ──►  نسخ احتياطي + مراقبة + توثيق تشغيلي
```

## المرحلة ١ — الاستجواب واستكشاف المتطلبات (`Grilling`)

- **الهدف:** كشف جميع الافتراضات الغامضة قبل إنشاء أي ملف كود في المشروع.
- **الخطوات العملية:**
  1. امنع النموذج صراحةً من كتابة الكود، واطلب منه محاورتك **بسؤال واحد في كل مرة** مشفوعاً بتوصيته الهندسية وسببها.
  2. حدّد تصنيف المشروع بوضوح: تجربة سريعة (`PoC` / `Software for One`) أم منتج بمستخدمين وبيانات حقيقية (`MVP / Production`).
  3. احسم الجمهور المستهدف، سير العمل الأساسي، حساسية البيانات، الأدوار والصلاحيات، حجم الضغط المتوقع، وما هو **خارج النطاق صراحةً** في الإصدار الأول.
- **معيار العبور:** زوال كل غموض في الفكرة والنطاق وتوثيق جميع القرارات كتابةً.

---

## المرحلة ٢ — تصميم النظام وكتابة المواصفات (`Specs Before Prompts`)

- **الهدف:** تثبيت ذاكرة المشروع الدائمة داخل ملفات المستودع حتى لا يضيع السياق بتغيّر الجلسات.
- **المخرجات المكتوبة:**
  - `AGENTS.md` / `CLAUDE.md` — دستور المشروع: التقنيات المعتمدة، هيكل المجلدات، الحد الأقصى لطول الدالة (`≤ 30` سطراً)، سياسة التبعيات، والخطوط الأمنية الحمراء.
  - `PRD.md` — وثيقة متطلبات المنتج، عقود الواجهات البرمجية، نموذج البيانات، وما لا يقل عن **١٥ حالة حدية ومساراً غير سعيد (`Edge & Unhappy Cases`)**.
- **معيار العبور:** قدرة أي مهندس أو جلسة وكيل جديدة على فهم حدود النظام كاملةً بمجرد قراءة الملفين.

---

## المرحلة ٣ — إعداد البيئة المعزولة واختيار طبقة الأدوات

- **الهدف:** اختيار الأداة التي تمنحك التحكم الكامل وتجهيز شبكة الأمان قبل كتابة الكود.
- **مقارنة طبقات الأدوات ومستوى التحكم:**

| طبقة الأداة | أمثلة النمط | مستوى التحكم | الاستخدام الأنسب |
| :--- | :--- | :--- | :--- |
| **منصات البناء السحابية الشاملة** | بُنّاة المتصفح من أمر واحد | محدود / مغلق | التحقق السريع من الأفكار (`PoC`) والعروض الأولية |
| **محررات الكود المدعومة بالذكاء الاصطناعي** | محررات سطح المكتب التفاعلية | مرتفع على مستوى الملفات | تطوير الميزات اليومية وإعادة الهيكلة |
| **وكلاء الطرفية ومساحة العمل** | `OpenCode` · `Claude Code` · `Codex CLI` | **تحكم كامل («القيادة اليدوية»)** | بناء منتجات `MVP` والإنتاج الكامل بانضباط هندسي |

- **خطوات التجهيز:**
  1. تهيئة مستودع `Git` نظيف + `.gitignore` + `.env.example`.
  2. تفعيل أدوات التنسيق والفحص الثابت (`Linter / Formatter / Typecheck`) وإطار الاختبارات منذ اللحظة الأولى.
  3. عزل صلاحيات الوكيل عن ملفات جهازك الشخصية وقواعد بيانات الإنتاج.
- **معيار العبور:** أول `Commit` نظيف يعمل فيه الفاحص الآلي ومشغّل الاختبارات بدون أي أسرار مكشوفة.

---

## المرحلة ٤ — وضع التخطيط المعتمد (`Plan Mode`)

- **الهدف:** مراجعة التصميم المعماري وتسلسل المهام واعتمادهما بشرياً **قبل** التنفيذ.
- **الخطوات العملية:**
  1. اطلب من الوكيل قراءة `AGENTS.md` و`PRD.md` وإخراج خطة تنفيذ مرحلية في ملف `IMPLEMENTATION_PLAN.md`.
  2. تحقّق من جدولة مجمّع اتصالات قاعدة البيانات (`Connection Pool`)، والتحقق الخادمي، وفحوص الصلاحيات، وتثبيت إصدارات المكتبات، وتوافق شاشات الهواتف.
  3. ناقش وعدّل أي قرار معماري مبالغ فيه أو ضعيف قبل منح الموافقة.
- **معيار العبور:** اعتماد ملف `IMPLEMENTATION_PLAN.md` وحفظه في المستودع.

---

## المرحلة ٥ — البناء المتسلسل المقسّم ونقاط الرجوع (`Checkpoints`)

- **الهدف:** بناء شرائح المشروع واحدةً تلو الأخرى دون ذبول برمجي أو كسر لما يعمل.
- **الخطوات العملية:**
  1. اطلب **طبقة أو شريحة واحدة في كل مرة**: `نموذج البيانات ← الـ API والتحقق ← منطق العمل ← الواجهة ← الاختبارات`.
  2. اقرأ `git diff` كاملاً قبل القبول؛ وتأكد من عدم لمس ملفات خارج النطاق وعدم إضافة مكتبات بلا مبرر.
  3. افحص تبويب `Network` (عدد الطلبات لكل شاشة) وطبقات الـ CSS في المتصفح عند بناء الواجهات.
  4. احفظ `git commit` ذرياً بعد كل شريحة ناجحة، وافتح جلسة محادثة جديدة عند الانتقال لوحدة مختلفة.
- **معيار العبور:** اكتمال شرائح الـ `MVP` بسجل `Git` نظيف وقابل للرجوع في أي لحظة.

---

## المرحلة ٦ — المراجعة الناقدة المستقلة واختبار المسارات غير السعيدة

- **الهدف:** إثبات مثلث الإنتاج (**الأمان · الأداء · قابلية الصيانة**) عبر طرف مستقل عن جلسة الكتابة.
- **الخطوات العملية:**
  1. شغّل **وضع النقد الصارم** (`vibe-critique`) في جلسة مستقلة أو بنموذج مختلف لمطابقة الكود مع `PRD.md`.
  2. دقّق جميع الاختبارات لكشف **الاختبارات المزيفة** (`vibe-test-gate`)، واشترط اختباراً يفشل أولاً ثم ينجح (`Fail-Then-Pass`) لكل إصلاح.
  3. نفّذ اختبارات المسارات غير السعيدة (مدخلات تالفة، صلاحيات غير مصرح بها، انقطاع الشبكة، هجمات `Prompt Injection`، واختبار ضغط `1000+` طلب).
  4. شغّل أدوات الفحص الأمني الثابت (`SAST`) وفحص ثغرات التبعيات.
- **معيار العبور:** تغطية كل متطلب في `PRD.md` باختبار حقيقي ناجح وخلو المشروع من الثغرات الحرجة والعالية.

---

## المرحلة ٧ — بوابة الإطلاق والبناء للمهندس القادم بعدك

- **الهدف:** ضمان صمود النظام أمام المستخدمين الفعليين وأعطال منتصف الليل وسهولة انتقاله لأي مهندس بعدك.
- **الخطوات العملية:**
  1. استوفِ البنود الـ ١٦ في [بوابة الإطلاق للإنتاج](checklists.ar.md#البوابة-٣--قبل-الإطلاق-بوابة-الإنتاج-والأمان).
  2. فعّل النسخ الاحتياطي الآلي **وجرّب استعادته فعلياً**، واضبط المراقبة والتنبيهات وخطة الطوارئ.
  3. وثّق طريقة التشغيل والقرارات المعمارية وخطوات النشر بوضوح.
- **معيار العبور:** قدرة مهندس آخر على فتح المستودع وفهم النظام وتشغيله والتعديل عليه بأمان خلال **ساعة واحدة** دون الرجوع إليك.

---

## مصفوفة المفردات التقنية الأساسية للمهندس الوكيلي

> *من لا يملك اسم المفهوم التقني لن يعرف كيف يطلبه بدقة ولا كيف يكتشف غيابه في المراجعة.*

| المحور | المفاهيم الجوهرية الواجب إتقانها |
| :--- | :--- |
| **البنية المعمارية** | Front-end مقابل Back-end · عقود REST / GraphQL · تصميم قواعد البيانات (`Schema`) · محركات البحث والفهرسة · الوحدات المعيارية والخدمات المصغرة |
| **السلوك والتزامن** | التوجيه (`Routing`) · المصادقة مقابل التفويض (`AuthN / AuthZ`) · أنماط العرض (`CSR / SSR / SSG`) · إدارة الحالة · مجمّع الاتصالات (`Connection Pool`) · أمان التزامن (`Thread-Safety`) |
| **الجودة والصيانة** | الكود النظيف (`Clean Code`) · أنماط التصميم · فصل المسؤوليات · الديون التقنية · الحالات الحدية · المسار السعيد وغير السعيد · المراجعة الناقدة |
| **التشغيل والأمان** | إدارة الفروع في `Git` · الحاويات (`Docker`) · خيارات الاستضافة · فحص `SAST` والأسرار · المراقبة والتنبيهات · النسخ الاحتياطي واختبار الاستعادة |

## خطة ٣٠ يوماً للانتقال العملي إلى الهندسة الوكيلية

| الأسبوع | محور التركيز | المخرج العملي الملموس |
| :--- | :--- | :--- |
| **الأسبوع ١** | **إتقان الأساسيات المعمارية** | القدرة على شرح رحلة الطلب كاملةً (`Routing ← Auth ← Validation ← DB Pool ← Render`) شفهياً وكتابياً دون مساعدة النموذج. |
| **الأسبوع ٢** | **المواصفات قبل البرومبت** | اختيار فكرة مشروع صغير وتطبيق المرحلتين ١ و٢ عليها لإنتاج `AGENTS.md` و`PRD.md` مع ١٥+ حالة حدية موثقة. |
| **الأسبوع ٣** | **البناء المتسلسل المنضبط** | تنفيذ المراحل ٣–٥ عبر `Plan Mode` والأوامر المقسّمة وقراءة كل `Diff` وبناء سجل `Commits` نظيف. |
| **الأسبوع ٤** | **التدقيق الأمني والإطلاق** | تنفيذ المرحلتين ٦ و٧: اختبارات المسارات غير السعيدة، فحص `SAST` والشبكة، استيفاء بوابة الـ ١٦ بنداً، ونشر المشروع بتوثيق كامل. |

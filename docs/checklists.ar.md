# قوائم التحقق الهندسية الثلاث وقاموس المصطلحات

**[🇬🇧 English Version](checklists.en.md)** · **[⬅ العودة إلى الدليل الرئيسي](../README.ar.md)**

تُستخدم قوائم التحقق الثلاث أدناه كبوابات إلزامية لا يُسمح بتجاوزها: قبل بدء المشروع، وأثناء قبول كل مهمة برمجية، وقبل الإطلاق على مستخدمين حقيقيين.

---

## البوابة ١ — قبل البدء (قائمة الجاهزية الذهنية والمعمارية)

- [ ] **١. وضوح الصفحة الواحدة:** هل أستطيع شرح مشكلة المنتج وسير عمله الأساسي بوضوح في صفحة واحدة؟
- [ ] **٢. تصنيف دورة الحياة:** هل حسمتُ نوع المشروع منذ البداية: تجربة مؤقتة (`PoC` / `Software for One`) أم نظام بمستخدمين وبيانات حقيقية (`MVP / Production`)؟
- [ ] **٣. المواصفات قبل أول أمر:** هل كتبتُ `AGENTS.md` (أو `CLAUDE.md`) و`PRD.md` داخل المستودع قبل إرسال أول برومبت؟
- [ ] **٤. حصر الحالات الحدية بشرياً:** هل فكرتُ بنفسي في ١٥ حالة حدية ومسار فشل على الأقل قبل طلب التنفيذ؟
- [ ] **٥. امتلاك المفردات التقنية:** هل أفهم آلية التوجيه، والمصادقة، ومجمّع الاتصالات، ونمط العرض (`CSR / SSR / SSG`)، وطريقة النشر المختارة؟
- [ ] **٦. اختيار أداة التحكم الكامل:** هل اخترتُ وكيل طرفية أو محرر كود يتيح قراءة كل `Diff` والتحكم الكامل في الملفات؟
- [ ] **٧. سقف الميزانية والتوكنز:** هل حددتُ سقفاً شهرياً واضحاً لتكلفة الاشتراكات واستهلاك الـ API؟
- [ ] **٨. تهيئة `Git` وأدوات الجودة:** هل المستودع مهيأ بملف `.gitignore` و`.env.example` وأدوات الفحص والاختبار قبل كتابة أول سطر مولّد؟

## البوابة ٢ — أثناء البناء (قائمة قبول كل مهمة على حدة)

- [ ] **١. أمر محدّد ومقيّد:** هل شمل الطلب التقنية، والنطاق، ومعايير القبول، **وما لا أريده صراحةً**؟
- [ ] **٢. شريحة واحدة فقط:** هل تُنفّذ هذه المهمة طبقة أو شريحة واحدة فقط بعيداً عن الأوامر الضخمة المتشعبة؟
- [ ] **٣. قراءة الـ `Diff` كاملاً:** هل قرأتُ جميع الأسطر المضافة والمعدلة قبل القبول دون أي قبول أعمى؟
- [ ] **٤. الفهم الكامل لكل سطر:** هل أفهم وظيفة كل سطر مقبول، وطلبتُ تفسير أي جزء غير مألوف قبل دمجه؟
- [ ] **٥. انضباط سلاسل الإمداد:** هل خلا التعديل من إضافة مكتبات خارجية لوظائف بسيطة يمكن كتابتها مباشرةً؟
- [ ] **٦. نظافة الأسرار:** هل جميع المفاتيح وبيانات الاعتماد مخزنة في `.env` وخالية تماماً من ملفات الكود وسجل `Git`؟
- [ ] **٧. التحقق المزدوج للمدخلات:** هل يتم التحقق من المدخلات في الواجهة (لتجربة المستخدم) وفي **الخادم إلزامياً** (للأمان)؟
- [ ] **٨. نقطة رجوع ذرية (`Checkpoint`):** هل سجلتُ `git commit` واضحاً فور التحقق من عمل هذه الشريحة؟
- [ ] **٩. عدم كسر ما يعمل:** هل شغّلتُ جميع الاختبارات السابقة وتأكدتُ من نجاحها دون أي تراجع؟
- [ ] **١٠. الخلو من الذبول البرمجي (`AI Slop`):** هل الدوال مركّزة (`≤ 30` سطراً)، بأسماء دلالية، وبلا تكرار أو تعليقات حشوية؟
- [ ] **١١. فحص مصداقية الاختبارات:** هل قرأتُ جمل التحقق (`Assertions`) وتأكدتُ أن الاختبار سيفشل فعلاً لو تعطّل الكود الأصلي؟
- [ ] **١٢. الدليل التشغيلي المباشر:** هل فحصتُ السجلات وتبويب `Network` وطبقات العرض بنفسي بدل الاكتفاء بكلمة «تم»؟

## البوابة ٣ — قبل الإطلاق (بوابة الإنتاج والأمان من ١٦ بنداً)

- [ ] **١. الفحص الأمني الثابت والتبعيات:** تشغيل `SAST` وفحص ثغرات المكتبات ومعالجة أي ثغرة حرجة أو عالية.
- [ ] **٢. دورة المصادقة والصلاحيات كاملةً:** اختبار التسجيل، الدخول، استعادة كلمة المرور، انتهاء الجلسة، تقييد المحاولات، وعزل صلاحيات المستخدمين.
- [ ] **٣. حزمة المسارات غير السعيدة:** اختبار المدخلات الشاذة، الصلاحيات الناقصة، انقطاع الشبكة، والطلبات المكررة.
- [ ] **٤. اختبار الضغط ومجمّع الاتصالات:** التحقق من ثبات النظام تحت `1000–2000` طلب متزامن مع تفعيل `Connection Pool`.
- [ ] **٥. مقاومة `Prompt Injection`:** فحص أي مدخلات نصية متصلة بنماذج لغوية ضد محاولات كسر التعليمات أو تسريب البيانات.
- [ ] **٦. التوافق عبر الأجهزة والمتصفحات:** التجربة الفعلية على الهواتف ومتصفحات Safari وFirefox وChrome.
- [ ] **٧. النسخ الاحتياطي وحماية الحذف:** جدولة نسخ احتياطي آلي **وتجربة استعادته فعلياً**، وحماية أوامر `DROP / DELETE` بتأكيد يدوي.
- [ ] **٨. المراقبة وخطة طوارئ منتصف الليل:** تفعيل رصد الأخطاء والتنبيهات الفورية وتوثيق خطة الاستجابة للحوادث.
- [ ] **٩. إزالة كافة البيانات التجريبية:** استبدال جميع النصوص والصور والبيانات البديلة (`Placeholders`) وفحص جميع الروابط.
- [ ] **١٠. تثبيت الإصدارات والأصول:** تثبيت إصدارات الحزم (`Lockfiles`) وتأمين الخطوط والأيقونات ضد انقطاع روابط `CDN`.
- [ ] **١١. كفاءة طلبات الشبكة:** مراجعة تبويب `Network` لكل شاشة والتأكد من عدم إرسال طلبات مكررة غير مرئية.
- [ ] **١٢. مراجعة أمنية مستقلة:** تنفيذ التقييم النهائي عبر مهندس بشري أو نموذج مستقل (وليس نفس النموذج الكاتب للكود).
- [ ] **١٣. كتابة سياسات الوصول من الصفر:** كتابة قواعد الصلاحيات بحدود صريحة وعدم نسخ أي برومبت صلاحيات بين الأدوات.
- [ ] **١٤. الامتثال القانوني والوصول والأصالة:** مراجعة سياسة الخصوصية، معايير إمكانية الوصول، وأصالة التصميم.
- [ ] **١٥. التوثيق للمهندس القادم:** جاهزية `README` وتوثيق المعمارية والتشغيل بحيث يفهمها مهندس جديد خلال أقل من ساعة.
- [ ] **١٦. اعتماد المسؤولية النهائية:** وجود مسؤول بشري واضح يملك القرار والقدرة على التدخل الفوري عند أي خلل إنتاجي.

## قاموس مصطلحات الهندسة الوكيلية

| المصطلح | التعريف الهندسي العملي |
| :--- | :--- |
| **Vibe Coding (الفايب كودينج)** | بناء البرمجيات بوصف الرغبات باللغة الطبيعية مع تجاهل الكود المولّد؛ ممتاز لإثبات الأفكار السريع (`PoC`) وخطر على منتجات المستخدمين الحقيقيين. |
| **Vibe / Agentic Engineering (الهندسة الوكيلية)** | قيادة وكلاء الذكاء الاصطناعي عبر مواصفات مكتوبة، ومهام مقسّمة، ومراجعة كاملة للـ `Diff`، ونقد صارم، واختبارات للمسارات غير السعيدة. |
| **AI Slop (الذبول البرمجي)** | كود متضخم غير منظم مليء بالتكرار والتعليقات العشوائية، يعمل ظاهرياً لكنه يدمر قابلية الصيانة. |
| **Complexity Ceiling (سقف التعقيد)** | المستوى المعماري والمنطقي الذي تتراجع بعده قدرة النماذج التوليدية الحرة وتبدأ في كسر الميزات القائمة. |
| **Truncation Patching (الترقيع التراكمي)** | إضافة طبقات التفاف وترقيع فوق العطل بدلاً من تشخيص السبب الجذري وإزالته. |
| **Sycophancy (التملّق)** | انحياز النموذج الافتراضي لمجاملة المستخدم وتأكيد افتراضاته بدل كشف الأخطاء — ويُعالَج بتفعيل وضع النقد الصارم. |
| **Grounding (التأريض)** | إسناد إجابات النموذج إلى مصادر موثقة وملفات فعلية ونتائج تشغيل بدلاً من التنبؤ الاحتمالي الحر. |
| **Test Theater (مسرح الاختبارات المزيّفة)** | اختبارات شكلية يكتبها النموذج لإظهار علامة النجاح الخضراء دون إثبات أي سلوك خارجي حقيقي. |
| **Chained Prompting (الأوامر المتسلسلة)** | تقسيم البناء إلى طبقات متعاقبة تُراجَع وتُختبَر وتُحفَظ كل طبقة منها قبل طلب التالية. |
| **`AGENTS.md` / `CLAUDE.md`** | ملف الدستور الهندسي الدائم داخل المستودع لضبط المعمارية ومعايير الكود والضوابط الأمنية في كل جلسة. |
| **`PRD.md`** | وثيقة متطلبات المنتج التي تترجم فكرة المشروع إلى متطلبات قابلة للاختبار وحدود نطاق وحالات حدية. |
| **Software for One (برمجيات الفرد الواحد)** | أدوات شخصية مخصصة لمستخدم واحد فقط — وهي أأمن منطقة لاستثمار سرعة التوليد المباشر. |
